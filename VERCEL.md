# Vercel / Supabase

Два проекта подключены к одному репозиторию и ветке main:

| Проект | Root Directory | Домен |
|---|---|---|
| Фронтенд | kisa-brend | kisa.deo-core.codes |
| Django | kisa_brend_back | kisa.backend.deo-core.codes |

Фронтенд использует `/api`. Vercel направляет эти запросы на домен Django. Правила маршрутов сохраняют прямое открытие страниц React. Не добавляйте секреты Supabase в переменные VITE_*.

К бэкенду подключена интеграция Supabase (Production). Django читает `POSTGRES_URL`, `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` автоматически. Можно задать отдельный `DJANGO_SECRET_KEY`; без него на Vercel используется HMAC от серверного секрета Supabase с отдельным назначением. Ротация исходного секрета завершает текущие сессии админки.

Во время production-сборки `build.py` создаёт отдельную схему `kisa`, применяет миграции и создаёт bucket `kisa-media` для публичных изображений/видео магазина. Клиентам Supabase не предоставляется доступ к заказам и персональным данным в этой схеме. Запись и удаление файлов выполняет только Django с серверным ключом. Существующий приватный bucket автоматически публичным не становится.

Каждая production-сборка проверяет загрузку и публичное чтение контрольного изображения, затем удаляет контрольный файл.

Демонстрационный каталог устанавливается командой `python manage.py seed_demo` один раз при production-сборке: 3 товара с 9 цветовыми вариантами, 5 размеров, 45 строк остатков, 2 коллекции и 3 публикации. Фотографии из исходных макетов загружаются в постоянное хранилище. Маркер `SeedRun` предотвращает повторное наполнение, восстановление удалённых демотоваров и сброс цен/остатков на следующих деплоях. Для локального наполнения сначала выполните миграции, затем ту же команду. Демотовары помечены в описаниях; перед реальными продажами проверьте цены, характеристики и наличие.

Каждый push в `main` запускает production-деплой бэкенда. Перед публикацией выполняется `migrate --noinput`. Миграции создавайте локально и коммитьте вместе с изменениями моделей: сборка проверяет наличие миграций и останавливается, если они забыты. Блокировка PostgreSQL не позволяет двум параллельным деплоям одновременно менять схему. Для сборки используется session-подключение `POSTGRES_URL_NON_POOLING` (или отдельный `MIGRATION_DATABASE_URL`); обычные запросы сайта продолжают использовать `POSTGRES_URL`. Preview-деплои не изменяют production-базу.

Для первого суперпользователя добавьте в проект бэкенда Vercel переменную `DJANGO_SUPERUSER_PASSWORD` только для Production и запустите новый production-деплой. По умолчанию логин — `admin`; его можно задать через `DJANGO_SUPERUSER_USERNAME`, email — через `DJANGO_SUPERUSER_EMAIL`. Пароль должен соответствовать проверкам Django. После успешного создания удалите переменную пароля из Vercel. Последующие сборки не меняют существующий пароль и не повышают права обычного пользователя.

Проверка работы: `/api/health/`, `/api/catalog/products/`, `/admin/login/`, загрузка изображения в админке и его URL в Supabase после следующего деплоя. Секреты не записывайте в Git.

DNS: записи CNAME `kisa` и `kisa.backend` в зоне `deo-core.codes` должны указывать на значения, показанные Vercel в Domains соответствующего проекта. Cloudflare Proxy: DNS only. Vercel выпускает HTTPS-сертификаты после проверки DNS.

В Vercel нет локального постоянного диска для загрузок. Redis здесь не требуется: корзина хранится в браузере, заказы и резервирование выполняются синхронно в PostgreSQL. Кэш текстов — локальный краткосрочный. Отправка рассылок и онлайн-эквайринг требуют отдельной настройки.
